# Pintia 自动答题与 AI 答案方案设计

## 1. 背景与问题

当前插件的核心价值已经比较明确：

- 能识别 Pintia 的题库数据
- 能导出结构化题目
- 能把题目发给自定义 API 模型
- 能返回 AI 分析文本

但从用户体验上仍然偏“工具型”，而不是“自动化助手型”。最核心的问题在于：

- 用户仍然需要手动配置 API Key、模型地址、Prompt
- 这对普通用户门槛偏高，而且大多数国内用户更习惯直接使用网页端大模型
- 即使拿到了答案，也只是展示文本，不能真正落到题目页面上
- 用户需要再次自己复制、粘贴、拼接答案，效率依然有限

因此，插件可以从“AI 辅助分析工具”升级成“AI 自动答题助手”，并把两条路线并行：

- 低门槛方案：网页 AI / 复制 Prompt / 一键跳转
- 专业方案：自定义 API 模型 / 高级 Prompt / 稳定输出

两者统一之后，插件会更实用，而且更符合国内用户的真实使用习惯。

---

## 2. 目标与原则

### 2.1 目标

1. 降低用户使用门槛
   - 支持网页端模型直接获取答案
   - 支持复制标准化 Prompt
   - 不强制要求用户填 API Key

2. 保留高级能力
   - 允许用户配置自定义模型
   - 支持 DeepSeek、豆包、OpenAI 等通用模型
   - 允许用户自定义 Prompt 和输出格式

3. 提升作业体验
   - 把 AI 结果解析为结构化答案
   - 自动填充到题目的相应输入框/选择器中
   - 自动检测题目状态与下一题推进
   - 允许暂停、继续、跳过和重试

4. 明确边界
   - 不自动提交
   - 不保存答案
   - 不绕过登录态
   - 不执行隐藏/违规操作
   - 只模拟用户在页面上的正常交互动作

### 2.2 原则

- 用户必须可见并可控：自动化不能完全黑盒运行
- 最小化风险：不做提交、不做保存、不做异常绕过
- 统一答案结构：AI 输出与自动填充逻辑分离
- 多入口共用：网页 AI 与 API 模型使用统一解析器
- 兼容性优先：尽量基于 DOM / 可见元素交互，而不是绕过页面

---

## 3. 核心产品思路

### 3.1 两种答案来源并行

#### 方案 A：网页端 AI 模式（主入口）

适合大多数用户。

功能：

- 一键复制当前题目 Prompt
- 一键打开大模型网页端
- 自动在新标签页打开模型站点
- 复制标准化题目 JSON / 文本
- 用户在网页 AI 中直接获得答案
- 插件负责收集、解析和回填

优点：

- 不需要配置 Key
- 不需要付费
- 适合国内大模型用户
- 无需学习 OpenAI 协议

缺点：

- 依赖第三方网页端服务状态
- 一次性答案可能需要手动复制
- 不如自定义 API 稳定

#### 方案 B：自定义 API 模式（专业模式）

适合高级用户。

功能：

- 配置 API 基础地址
- 配置模型名称
- 配置 API Key
- 配置 Prompt 模板
- 支持 Chat Completions / Responses 等接口兼容格式

优点：

- 可控稳定
- 可批量处理
- 适合长期使用

缺点：

- 配置门槛高
- 可能产生费用

### 3.2 最终统一入口

无论答案来自哪一条路，插件最终都把它转换成统一的结构化答案对象：

```json
{
  "questionId": "xxx",
  "questionNumber": 1,
  "type": "single_choice",
  "source": "web-ai",
  "status": "parsed",
  "answer": "B",
  "rawText": "B",
  "confidence": "medium"
}
```

这样后续自动答题逻辑就不需要区分来源，只依赖统一结构。

## 4. 题目 Prompt 设计

### 4.1 目标

让模型返回稳定且可解析的答案，而不是自由散文。

### 4.2 通用输出格式

建议对所有题型要求固定返回结构，例如：

```text
请根据题目信息直接给出最终答案，不要解释过程。

输出格式必须严格遵守以下 JSON 规范：
{
  "questionNumber": 1,
  "type": "single_choice",
  "answer": "B"
}

如果是多选题：
{
  "questionNumber": 2,
  "type": "multiple_choice",
  "answer": ["A", "C"]
}

如果是判断题：
{
  "questionNumber": 3,
  "type": "true_false",
  "answer": true
}

如果是填空题：
{
  "questionNumber": 4,
  "type": "fill_blank",
  "answer": ["10", "x+y"]
}

如果是编程题：
{
  "questionNumber": 5,
  "type": "programming",
  "answer": "<可提交代码>"
}

如果是简答题：
{
  "questionNumber": 6,
  "type": "short_answer",
  "answer": "简答内容"
}

只输出 JSON，不要 markdown，不要额外说明。
```

### 4.3 适配网页 AI 的复制逻辑

插件会在以下场景生成 Prompt：

- 当前作业题库已检测成功
- 用户选择了某些题型
- 用户点击“复制题目 Prompt”
- 插件生成：
  - 标题
  - 题目列表
  - JSON 结构
  - 输出格式要求
  - 题型约束

这样用户无需手动整理题目内容，直接复制到网页端 AI 即可。

## 5. 自动答题方案设计

### 5.1 设计目标

自动答题的核心不在于“提交”，而在于“模拟正常用户在页面上的输入行为”。

因此，插件的自动答题逻辑必须：

- 只填充当前题目的答案
- 不提交、不保存
- 可暂停、可继续、可跳过
- 可检测页面是否进入下一题
- 允许用户确认后再继续

### 5.2 可行的自动化方式

优先采用以下方式：

1. 识别页面题型元素
   - 单选题：radio / input / label / button
   - 多选题：checkbox / label
   - 判断题：radio / button
   - 填空题：input / textarea / contenteditable
   - 编程题：textarea / code editor
   - 简答题：textarea

2. 选择器优先级
   - 先找稳定属性，如 data-*、name、id、class 特征
   - 再找标准题目结构
   - 再退回到文本定位 + 关键词匹配

3. 低风险动作
   - 点击选项
   - 赋值 input.value
   - dispatchEvent(new Event('input'))
   - dispatchEvent(new Event('change'))
   - keyup / blur 触发

4. 不做的动作
   - 不提交答案
   - 不点击“保存”
   - 不强制页面跳转
   - 不绕过前端校验

### 5.3 状态机设计

建议实现如下状态机：

```text
idle
  -> detecting
  -> generating
  -> parsing
  -> filling
  -> paused
  -> completed
  -> failed
```

每个状态都有明确处理：

- `detecting`：检测当前页面是否为进行中题目
- `generating`：获取 AI 答案
- `parsing`：解析结构化答案
- `filling`：逐题写入 DOM
- `paused`：等待用户点击继续
- `completed`：当前题库/当次任务已处理
- `failed`：出现错误，输出日志

### 5.4 自动化执行策略

推荐“逐题执行”而非“一次性全填”：

- 先获取本题答案
- 解析成功后，回填当前题
- 进入下一题前检测页面状态
- 如果发现题目已切换，继续进行下一题
- 允许用户在任一时刻暂停

这比一次性大批量填充更稳定，也更兼容页面动态加载。

## 6. 检测答题状态的实现思路

### 6.1 为什么需要检测

自动答题不能盲目执行，否则容易出现：

- 页面还没加载完
- 答题状态异常
- 当前题目不一致
- DOM 已发生变化
- 题目内容已被切换或重置

因此需要检测三类状态：

1. 当前页面是否是题目页
2. 当前题目是否已加载
3. 当前题目是否已完成或已提交

### 6.2 检测项

- 是否还在作业页面
- 是否存在当前题目的容器
- 是否存在题目标题、题干内容
- 是否有选项节点
- 是否存在下一题按钮
- 是否存在“提交 / 保存 / 下一题 / 完成”状态
- 当前页面是否已经提交过答案

### 6.3 处理策略

- 页面未准备好：等待重试
- 当前未定位到题目：暂停并提示
- 页面已切到下一题：自动继续
- 页面已提交：结束任务并提示“已结束当前题目流程”

## 7. 页面设计方案

### 7.1 设计方向：悬浮助手面板

不建议做成控制台式的原始黑底面板，而是建议做成“右侧悬浮助手”。

结构建议：

- 顶部状态栏：检测状态、AI 状态、任务状态
- 中间区：题目概览与题型选择
- 操作区：复制 Prompt、打开网页 AI、生成答案、开始自动填题、暂停、继续
- 日志区：本轮解析结果、写入状态、错误信息

### 7.2 交互方式

- 默认最小化状态：只显示状态小条
- 点击展开：显示详细控制
- 支持拖拽/固定位置
- 支持“置顶悬浮”但不要遮挡核心页面内容

### 7.3 页面展示的重点

- 当前题库数量
- 当前检测是否成功
- AI 来源：网页 AI / API
- 当前题型选择
- 自动填题状态
- 最后一次成功解析结果
- 当前执行日志

## 8. 功能模块拆分

### 8.1 模块一：题库与 Prompt 提取

职责：

- 检测当前 Pintia 页面
- 提取题库
- 按题型归一化
- 生成统一的题目对象
- 生成复制型 Prompt

### 8.2 模块二：答案生成

职责：

- 支持网页 AI Prompt 复制
- 支持 API 模型调用
- 统一输出结构
- 处理模型返回失败与重试

### 8.3 模块三：答案解析

职责：

- 解析文本/JSON
- 规范化答案格式
- 按题型输出标准答案对象
- 跟踪解析失败原因

### 8.4 模块四：自动填题

职责：

- 定位当前题目的 DOM
- 识别题型
- 选择填充策略
- 派发输入事件
- 检测是否成功写入

### 8.5 模块五：任务控制

职责：

- 启动/暂停/继续/停止
- 检测页面变化
- 跳过失败题目
- 定时重试
- 结束任务提示

---

## 9. 实施优先级

### 第 1 阶段：低门槛价值

- 网页 AI Prompt 复制
- 题目导出/格式化
- 自定义 API 配置保留
- 统一答案对象

### 第 2 阶段：解析与回填

- AI 返回解析
- 标准题型解析
- 自动填空/单选/判断题回填
- 逐题状态检测

### 第 3 阶段：自动流程

- 自动切题
- 继续/暂停/重试
- 错误日志
- 任务完成提示

### 第 4 阶段：体验增强

- 悬浮面板
- 任务状态可视化
- 历史答案缓存
- 一键恢复上次任务

---

## 10. 建议的最终产品形态

最终版插件应该更像：

- 一个“Pintia 学习助手”
- 不是纯导出工具
- 也不是单纯的 AI Chat
- 而是“AI + 自动填题 + 状态控制”一体化工具

它应该满足：

- 普通用户可以直接开箱用网页 AI
- 高级用户可以用自建 API
- 用户可以拿到答案并在页面上自动回填
- 不提交、不保存、可控、透明

这才是当前插件真正可持续的方向。

---

## 11. 结论

目前这个插件已经具备“题库识别”和“AI 回答”两项基础能力，但还没有真正升级到“自动答题助手”的高度。最关键的改造方向不是增加更多配置项，而是：

- 把“网页 AI”作为主入口
- 把“自定义 API”作为高级入口
- 把“答案解析”统一成标准结构
- 把“自动填题”做成可控状态流

这样才会真正解决用户最痛的地方：低门槛拿答案 + 自动落到页面上 + 可暂停和控制。

这个方案的落地价值远高于单纯提供一个 API Key 配置页，也更容易被用户接受。
