# 开发规约

本文约定 Pintia 学习辅助工具的代码组织、实现边界和交付检查。新增功能和修复问题时应遵循本规约；如果确实需要改变既有约定，应在同一变更中说明原因并同步更新相关文档。

## 核心原则

- 先确认需求、现有行为和相关模块，再动手修改；优先修复根因，不顺手重构无关代码。
- 一个模块只负责一类明确职责。先在现有模块内按职责组织；当逻辑需要独立测试、被多处复用或明显妨碍理解时，再拆分文件。
- 不为一次性需求提前建立通用框架、层层封装或可配置选项。新增抽象必须解决已存在的重复或复杂度。
- 用户可见行为、消息结构、存储结构和导出格式都视为契约；调整时检查所有调用方和对应文档。
- 错误应在发生处保留原因，并通过现有界面或消息响应让用户知道失败；不静默忽略，不用成功结果掩盖失败。

## 文件和目录放置

```text
manifest.json
src/
  background/  扩展后台、跨页面消息、配置存储和模型请求
  content/     Pintia 页面提取、助手面板、答案校验与回填
  popup/       工具栏弹窗
  settings/    AI 配置页面
  shared/      多个运行环境确实共用的纯逻辑和默认配置
docs/          产品行为、数据契约、设计与开发规约
```

- 新代码放到最贴近其运行环境和职责的目录，不在仓库根目录散放脚本、临时文件或新功能模块。
- `shared/` 只放确实被多个扩展上下文使用的逻辑；页面专属代码留在 `content/`、`popup/` 或 `settings/`。
- 文件名使用小写 kebab-case，并体现职责，例如 `answer-runner.js`。沿用相邻文件的命名和组织方式。
- CSS、HTML 和脚本放在对应页面/功能目录。只有确实跨页面复用的资源才提升到共享目录。
- 单个文件变得难以定位职责时，按职责拆分并同步调整 `manifest.json` 或 HTML 的加载入口；不要仅为缩短文件长度机械拆分。
- 新增或移动文件后，检查 `manifest.json`、HTML 引用、相对路径、文档目录树和忽略规则。

## 架构和接口约定

### Manifest V3 与脚本加载

- 本项目没有打包步骤，`manifest.json` 和 HTML 中列出的文件顺序就是运行时依赖顺序。
- 内容脚本按经典脚本方式运行，不可直接使用 ES module 的 `import`/`export`。共享能力需沿用现有显式全局命名空间模式，并在入口中先加载依赖、后加载使用者。
- 新增后台依赖时检查 `service-worker.js` 的 `importScripts()` 顺序；新增内容脚本时检查 `content_scripts.js` 顺序。
- 脚本之间避免隐式依赖未声明的全局变量。使用项目已有命名空间，保持模块 API 小而清晰。

### 消息、存储和数据契约

- `chrome.runtime` 消息使用明确且稳定的 `type`，发送方和接收方共同维护字段结构。异步监听器必须正确保持消息通道，并处理 `runtime.lastError` 和响应中的错误。
- 修改消息、`chrome.storage.local` 配置或数据迁移时，检索所有读写方；兼容旧值时集中处理，不在多个 UI 页面各自猜测默认值。
- 题目导出、Prompt 输入和答案 JSON 的字段必须与 [答案 JSON 契约](./answer-json-contract.md) 一致。不得通过题号、题干或选项文本推断 `problemId`。
- Prompt 的默认版本集中维护在 `src/shared/prompt-builder.js`；不要在 popup、content 和后台各维护一份默认提示词。
- 答案 JSON 校验集中维护在 `src/shared/answer-contract.js`，供后台复核结果和页面回填共用；不要复制答案契约规则。
- AI 单次请求超时默认值通过 `PintiaAiConfig.defaults` 提供。自动回填/保存与诊断日志由答案助手面板统一控制，并通过后台消息持久化；诊断日志不得包含 API Key、提示词、题目或答案内容。
- 页面提取后的归一化字段和原始 `apiData` 各有用途。新增字段时说明其稳定含义，不要无故丢弃原始数据或让调用方依赖未归一化字段。

## 编码和错误处理

- 延续相邻代码风格：缩进、引号、命名、DOM 查询方式和异步模式保持一致。变量与函数名表达业务意图，避免无意义缩写。
- 函数保持单一职责；复杂流程拆成可命名的小步骤，但避免只转调一次且没有业务含义的包装函数。
- 输入数据、模型响应和页面 DOM 均视为不可信或可能缺失。使用明确校验和边界检查，不假定 API 响应或控件一定存在。
- Promise、网络请求、Chrome API 和 DOM 操作可能失败。保留可诊断的错误信息，并在合适的边界转换为用户可理解的提示。
- 不添加无关注释；注释用于解释约束、原因或不明显的兼容逻辑，而非复述代码。
- 不吞异常、不返回伪造的成功/空数据，也不通过宽泛 `catch` 让后续逻辑在无效状态下继续。

## Pintia 页面和 DOM 变更

- Pintia 的接口、页面结构和控件标记可能变化。接口匹配规则、字段归一及 JSON/Protobuf 解析集中在 `src/content/api-extractor.js` 与 `src/content/extractor-common.js` 的现有职责范围内。
- 依赖页面 DOM 的逻辑应使用可解释、尽量精确的标识；特别是答案回填必须按唯一 `problemId` 定位。禁止用模糊文本匹配兜底回填到其他题目。
- 页面异步加载、分页、题型切换和重复触发都要考虑。复用已有等待、缓存、校验与任务编排逻辑，避免增加重复请求或竞态。
- 回填行为会改变用户作答并可能触发保存。保持明确的用户触发边界、题型筛选、逐题验证和失败报告；自动回填相关默认值应保持谨慎，任何行为改变都要同步更新产品说明和回填设计。
- 页面选择器、导航 ID、接口路径、请求格式发生变化时，更新 [答案回填设计](./answer-fill-design.md) 或产品说明中的对应约定。

## 权限、密钥和用户数据

- 扩展权限遵循最小化原则。新增 `permissions`、`host_permissions` 或主机访问范围前，确认功能确实需要，并同步说明用途。
- API Key 和 AI 配置只能通过扩展存储管理，不得写入源码、日志、错误提示、导出题库或提交记录。向非扩展页面返回配置时，不暴露 API Key。
- 只有用户主动发起 AI 分析时才向配置的模型服务发送题目数据；新增外部请求、数据字段或数据去向时，明确告知用户并更新文档。
- 不读取或要求用户复制 Cookie，不绕过登录、站点权限或隐藏答案。访问 Pintia 登录态时遵循当前页面上下文与现有 `credentials` 处理方式。
- 修改 HTML 时避免将外部或页面内容直接拼入 `innerHTML`；需要插入动态文本时使用 `textContent` 或安全的 DOM API。若使用模板 HTML，确保插值只来自受控常量，并对不可信内容做安全处理。

## UI 与交互

- 维持 popup、助手面板和设置页各自的职责，不将业务处理堆入事件回调或 UI 渲染代码。
- 操作应提供明确的加载、成功和失败反馈；异步操作要防止重复提交或让用户误以为已完成。
- 改动页面布局或交互时，检查窄窗口、长错误文本、键盘可操作性和现有视觉样式；保持相关 CSS 与页面目录一致。
- 会改变题目、答案、保存或外部请求状态的动作必须明确可见，不增加隐式自动行为。

## 验证和交付

仓库目前没有 `package.json`、构建步骤或自动化测试命令。提交前按变更范围执行可用检查，不要声称未运行的测试已通过。

1. 检查变更范围：`git diff --check`，确认没有无关文件、调试输出或密钥。
2. 对修改过的 JavaScript 文件逐个执行 `node --check <文件路径>`。
3. 修改 `manifest.json` 时确认 JSON 可解析、入口路径存在、脚本依赖顺序正确。
4. 涉及页面或浏览器行为时，在 Chrome 或 Edge 加载未打包扩展，验证相应流程与失败路径；涉及 Pintia 页面时在可用的测试题集上验证，避免在真实作业上试验保存行为。
5. 修改消息、数据格式、导出、Prompt 或答案回填时，检查其上下游调用方，并同步更新相关契约、设计文档和 README。
6. 最终说明做了什么、运行了哪些检查，以及尚未验证的浏览器或站点行为。

## 文档维护

- 用户可见功能、安装/权限/数据处理方式变化时更新 `README.md` 或 `docs/product.md`。
- JSON 字段、消息结构、配置格式变化时更新相应契约和迁移说明。
- 页面定位、注入、验证、保存流程变化时更新 `docs/answer-fill-design.md`。
- 保持文档中的目录树、文件名、默认行为和代码实现一致；删除或移动文件时一并清理过期引用。
